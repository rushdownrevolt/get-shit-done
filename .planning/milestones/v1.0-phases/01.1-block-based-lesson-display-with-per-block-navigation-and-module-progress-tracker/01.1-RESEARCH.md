# Phase 01.1: Block-based lesson display with per-block navigation and module progress tracker - Research

**Researched:** 2026-03-12
**Domain:** Terminal UI refactoring -- lesson renderer, navigator, and progress display
**Confidence:** HIGH

## Summary

This phase transforms the lesson display from rendering all content sections at once into a "part-by-part" navigation model. Each element in the lesson JSON `content` array becomes one "part" shown on a single screen. The user advances through parts with `w`, goes back with `q`, and skips entire lessons with `e`. A dot-based progress tracker shows position within the lesson. A celebratory banner fires when the user completes the last part of the last lesson in a module.

The existing codebase is well-structured for this change. The renderer (`renderer.cjs`) is already a pure function returning a string -- it just needs to be refactored from rendering ALL content sections to rendering a SINGLE content section (part) with pinned objective/criteria headers. The navigator (`navigator.cjs`) currently has a flat lesson-level loop -- it needs an inner part-level loop. The key remapping (w/q/e/esc replacing n/p/q) is a straightforward change to `waitForKey()`.

**Primary recommendation:** Refactor renderer.cjs to accept a part index parameter, add inner part-navigation loop to navigator.cjs, and build progress dot + completion banner as new rendering functions in renderer.cjs. No JSON schema changes needed.

### Pattern 1: Part-based Rendering
**What:** Refactor `renderLesson()` to `renderPart()` that renders a single content section with pinned header/footer.
**When to use:** Every screen render during lesson navigation.

```javascript
// Signature change
function renderPart(lesson, partIndex, totalParts, currentLessonIndex, totalLessons) {
  const parts = [];

  // 1. Clear screen
  parts.push(clearScreen());

  // 2. Lesson title + lesson position
  parts.push(style(lesson.title, 'bold', 'cyan'));
  parts.push('\n');
  parts.push(style('Lesson ' + (currentLessonIndex + 1) + ' of ' + totalLessons, 'dim'));
  parts.push('\n\n');

  // 3. Pinned objective header
  parts.push(style("What you'll learn:", 'yellow', 'bold'));
  parts.push('\n');
  parts.push(lesson.objective);
  parts.push('\n\n');
  parts.push(horizontalRule(60));
  parts.push('\n\n');

  // 4. Block header (dim label for content type)
  const section = lesson.content[partIndex];
  parts.push(style(getBlockLabel(section, partIndex), 'dim'));
  parts.push('\n\n');

  // 5. Single content section
  // ... render section by type (text/code/project) ...

  // 6. Pinned success criteria footer (concept map placement: discretion)
  parts.push(horizontalRule(60));
  parts.push('\n\n');
  parts.push(style("You'll know you've got it when:", 'green', 'bold'));
  parts.push('\n');
  parts.push(lesson.successCriteria);
  parts.push('\n\n');

  // 7. Progress dots
  parts.push(renderProgressDots(partIndex, totalParts));
  parts.push('\n\n');

  // 8. Navigation footer
  parts.push('  [w] Next  [q] Back  [e] Skip lesson  [c] Copy  [esc] Quit');
  parts.push('\n');

  return parts.join('');
}
```

### Pattern 2: Inner Part Navigation Loop
**What:** Navigator needs a two-level loop: outer for lessons, inner for parts within a lesson.
**When to use:** The main `runNavigationLoop` refactor.

```javascript
// Current: flat lesson loop
// New: lesson loop contains part loop
async function runNavigationLoop(lessons, startIndex, renderFn, progressFn, opts) {
  let currentLesson = startIndex;

  while (currentLesson < lessons.length) {
    const lesson = lessons[currentLesson];
    const totalParts = lesson.content.length;
    let currentPart = 0;

    while (currentPart < totalParts) {
      renderFn(lesson, currentPart, totalParts, currentLesson, lessons.length);
      const action = await waitForKey();

      if (action === 'next') {
        if (currentPart < totalParts - 1) {
          currentPart++;
        } else if (currentLesson < lessons.length - 1) {
          // Last part of lesson -> advance to next lesson
          currentLesson++;
          progressFn(currentLesson);
          break; // exits inner loop, outer loop picks up next lesson
        } else {
          // Last part of last lesson -> module complete
          // Show completion banner
        }
      } else if (action === 'prev') {
        if (currentPart > 0) currentPart--;
        // At first part: do nothing (can't go to previous lesson's parts)
      } else if (action === 'skip') {
        // Skip to next lesson
        if (currentLesson < lessons.length - 1) {
          currentLesson++;
          progressFn(currentLesson);
          break;
        }
      } else if (action === 'copy') {
        // Copy full lesson (unchanged behavior)
      } else if (action === 'quit') {
        progressFn(currentLesson);
        return;
      }
    }
  }
}
```

### Pattern 3: Progress Dot Rendering
**What:** Pure function generating the dot indicator line.

```javascript
function renderProgressDots(currentPart, totalParts) {
  const filled = '\u25cf'; // ●
  const empty = '\u25cb';  // ○
  const dots = [];
  for (let i = 0; i < totalParts; i++) {
    dots.push(i <= currentPart ? filled : empty);
  }
  return '  ' + dots.join(' ') + '  Part ' + (currentPart + 1) + ' of ' + totalParts;
}
```

### Pattern 4: Module Completion Banner
**What:** Colorful banner displayed after the user presses 'w' on the final part of the final lesson.

```javascript
function renderCompletionBanner(moduleTitle, lessonCount, totalParts, miniProjectCount) {
  const width = 50;
  const bar = style('\u2588'.repeat(width), 'cyan'); // or chosen color
  const parts = [];

  parts.push(bar + '\n');
  parts.push('\n');
  parts.push(style('  MODULE COMPLETE!', 'bold', 'cyan') + '\n');
  parts.push('\n');
  parts.push(style('  ' + moduleTitle, 'bold') + '\n');
  parts.push('\n');
  parts.push('  Lessons: ' + lessonCount + '\n');
  parts.push('  Parts: ' + totalParts + '\n');
  parts.push('  Mini-projects: ' + miniProjectCount + '\n');
  parts.push('\n');
  parts.push(bar + '\n');
  return parts.join('');
}
```

### Anti-Patterns to Avoid
- **Modifying lesson JSON files:** The content array is the part boundary. No schema changes.
- **Breaking renderLesson() callers:** The old function signature is used in gsd-learn.cjs -- if renaming, update all call sites.
- **Storing part-level progress in progress.json:** Part position is ephemeral (session-only). Only lesson-level progress persists across sessions. Adding part tracking to progress.json adds complexity for no user value.
- **Making concept map a separate "part":** The concept map is lesson-level context (like objective). It should be pinned or placed in a non-content-section way -- not treated as a content section since it is not in the content array.

## Common Pitfalls

### Pitfall 1: Navigation Edge Cases
**What goes wrong:** User presses 'q' (back) on first part of first lesson, or 'w' (next) on last part of last lesson without proper boundary handling.
**Why it happens:** Two-level navigation (lesson + part) has more edge cases than flat navigation.
**How to avoid:** Explicitly handle all boundary conditions: first part of lesson, last part of lesson, first lesson, last lesson. The 'w' on final-part-of-final-lesson triggers the completion banner (not a no-op).
**Warning signs:** Navigation "wraps around" or crashes at boundaries.

### Pitfall 2: Concept Map is Not in Content Array
**What goes wrong:** Code treats conceptMap as a content section and creates a "part" for it, but conceptMap is a top-level lesson field (string key), not a content array element.
**Why it happens:** Confusing lesson.conceptMap (string like "entry-point") with content sections (objects with type field).
**How to avoid:** Concept map is rendered by `renderConceptMap()` from concept-map.cjs. It must be handled separately -- either pinned to every part or given its own special part outside the content array. Recommended: give it its own "part" appended after content sections, or pin it as a small element.
**Warning signs:** Part count doesn't match content array length, or concept map disappears.

### Pitfall 3: Clipboard Copy Must Still Copy Full Lesson
**What goes wrong:** Copy action only copies the current part instead of the full lesson.
**Why it happens:** If copy handler is updated to use part-based data instead of full lesson.
**How to avoid:** The 'c' handler calls `formatLessonForClipboard(lessons[current], ...)` which iterates ALL content sections. Keep this unchanged -- pass the full lesson object, not just the current part.

### Pitfall 4: waitForKey Return Values Must Match New Keys
**What goes wrong:** Key handler returns 'next'/'prev' but the new keys are w/q/e/esc, and the navigator loop checks for old action names.
**Why it happens:** Partial update -- keys changed but action names didn't, or vice versa.
**How to avoid:** Define clear action names: 'next' (w), 'prev' (q), 'skip' (e), 'copy' (c), 'quit' (esc/Ctrl+C). Update both waitForKey() and the loop that reads its return value.

### Pitfall 5: Existing Tests Reference Old Key Names and Footer Text
**What goes wrong:** Tests fail because they check for `[n] Next` and `[p] Previous` in footer.
**Why it happens:** renderer.test.cjs explicitly asserts `[n]`, `[p]`, `[q]` in footer.
**How to avoid:** Update test assertions to match new footer: `[w] Next  [q] Back  [e] Skip lesson  [c] Copy  [esc] Quit`.

### Pitfall 6: Mini-Project Lesson Has Only 3 Content Sections
**What goes wrong:** The progress dots look sparse (3 dots) for the mini-project lesson while other lessons have 9-12 dots.
**Why it happens:** Lesson 06-mini-project.json has only 3 content sections (text, text, project).
**How to avoid:** This is fine -- it accurately represents the lesson structure. No special handling needed. The user will simply advance through 3 parts quickly.

## Open Questions

1. **Concept map placement -- own part or pinned?**
   - What we know: conceptMap is a top-level lesson field (not in content array). It's rendered via renderConceptMap() which returns an ASCII diagram.
   - What's unclear: Should it be a pinned element on every part (adds vertical space), its own synthetic "part" appended to content (clean separation), or only shown on the first/last part?
   - Recommendation: Give it its own synthetic part appended after the last content section. This keeps each screen focused on one concept, and the concept map serves as a "where you are in the architecture" summary before success criteria. (Claude's discretion)

2. **Arrow key aliases**
   - What we know: Current code maps right arrow to 'next' and left arrow to 'prev'. User said "removed or remapped."
   - What's unclear: Keep as aliases or remove entirely?
   - Recommendation: Remove arrow keys entirely to avoid confusion with the new scheme. Users adapting to new keys should not have silent aliases. (Claude's discretion)

3. **Navigation at lesson boundaries**
   - What we know: Pressing 'w' on last part should advance to next lesson. Pressing 'q' on first part could either do nothing or go back to previous lesson's last part.
   - What's unclear: Should 'q' on first part go to previous lesson?
   - Recommendation: 'q' on first part does nothing (stays on first part). Going back to a previous lesson is a different mental action than going back one part. The user has 'e' for lesson-level skipping but no "previous lesson" key -- this keeps the model simple.
