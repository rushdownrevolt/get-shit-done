# Phase 01.2: Adaptive per-part lesson structure with progressive content accumulation - Context

**Gathered:** 2026-03-12 (updated 2026-03-12)

<domain>
## Phase Boundary

Replace the single-block-per-screen renderer from Phase 01.1 with a progressive accumulation model: each "next" press adds a new block to the screen (blocks 1, then 1+2, then 1+2+3...). Add per-block contextual framing (focus lines, bridge teasers) and update the lesson JSON schema with new required fields. Regenerate all 6 existing lessons to include the new fields.

</domain>

<decisions>
## Implementation Decisions

### Rendering model — Progressive accumulation
- Each press of 'w' adds the next block to the screen — content accumulates
- Part 1 shows block 1; Part 3 shows blocks 1+2+3; Part N shows blocks 1..N
- All prior blocks render in full (no collapsing, no dimming) — user scrolls up to review
- Going back ('q') shrinks: removes the last block, re-renders with fewer blocks
- Clear screen on each navigation — fresh render of accumulated blocks each time

### Block grouping — code/diagrams always wrapped by text
- A code block or diagram MUST NEVER appear as a standalone part — it must always be grouped with surrounding text
- Grouping rule: lead-in text + code/diagram + explanation text = one combined part
- Text-only blocks remain their own standalone part (no aggressive grouping of text+text)
- Focus and bridge fields apply per-group, not per-block — each group gets one focus line and one bridge
- The renderer (or a pre-render step) auto-groups content: when a code/diagram block is encountered, it merges with adjacent text blocks into a single rendered part

### Block separation
- Dim horizontal rule between each accumulated group (not between blocks within a group)
- Current (newest) group gets a ▶ marker on its focus line — prior groups have no marker
- Prior groups render at normal brightness (not dimmed)

### Per-group focus lines (JSON field: `focus`)
- Each group gets a required `focus` string — a short phrase describing what THIS group teaches
- Replaces the old `getBlockHeader()` first-sentence extraction
- Displayed above the group's content, styled dim
- Current group's focus prefixed with ▶ marker

### Contextual bridges (JSON field: `bridge`)
- Each group gets a required `bridge` string — a sentence connecting this group to the next
- Displayed after the group content, before the separator, in a bordered section
- Bridge for the last group in a lesson bridges to the NEXT LESSON (title + preview)
- Last lesson's last group: bridge to success criteria or module completion

### Lesson-level objective and success criteria — KEPT
- Lesson `objective` field stays — displayed on Part 1 only (before first block)
- Lesson `successCriteria` field stays — displayed on last part only (after all blocks)
- Per-block `focus` is additive, not a replacement for the lesson objective

### JSON schema changes
- `focus` — required string on group-level content items (the lead text block of a group, or standalone text blocks)
- `bridge` — required string on group-level content items
- Code/diagram blocks within a group do NOT need their own focus/bridge — the group's lead text block carries them
- Both fields are REQUIRED on group-anchor blocks — lessons without them should fail at load time
- Lesson-level `objective` and `successCriteria` remain unchanged

### Lesson regeneration
- Update prompt templates to request `focus` and `bridge` fields per content item
- Re-run generate-lessons.cjs for all 6 existing lessons
- Review output for quality before committing
- This is a full regeneration, not a patch

### Claude's Discretion
- Exact bridge wording and tone
- Focus line styling (dim, color, etc.)
- How the ▶ marker is styled
- Bridge section border style
- How bridge-to-next-lesson differs visually from bridge-to-next-block
- Whether concept map gets its own focus/bridge or is handled differently
- Whether grouping lives in JSON schema (explicit group arrays) or renderer (auto-detection of code/text adjacency)

<specifics>
## Specific Ideas

- User's core motivation: the repeated objective/criteria on every screen was "far more distracting than intended" — per-block focus solves this by making each screen's framing unique
- Block headers from Phase 01.1 (first-sentence extraction) felt like "literally the same text but truncated" — authored `focus` fields give real descriptive headers
- Progressive accumulation gives a "growing document" feel — more satisfying than isolated screens
- The bridge teasers create narrative momentum between blocks, making the lesson feel like a guided journey
- This is explicitly experimental ("this is a big change and it's only a test") — quality of authored focus/bridge text will determine if the model works
- Code snippets and diagrams appearing alone with no surrounding text are disorienting — they need lead-in context and follow-up explanation to be useful as a "part"

</specifics>
