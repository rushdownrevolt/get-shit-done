# Phase 01.2: Adaptive per-part lesson structure with progressive content accumulation - Research

**Researched:** 2026-03-12
**Domain:** Terminal renderer refactoring, JSON schema evolution, lesson regeneration
**Confidence:** HIGH

## Summary

This phase replaces the single-block-per-screen renderer (`renderPart`) with a progressive accumulation model where each "next" press adds a new content block to the screen. It also adds two new required JSON fields (`focus` and `bridge`) to every content item, updates prompt templates to request these fields, and regenerates all 6 existing lessons.

The codebase is well-structured for this change. The renderer is a pure function returning ANSI strings, the navigator already tracks `partIndex` and passes it to `renderPart`, and lesson loading validates required fields. The main work is: (1) refactoring `renderPart` to loop from block 0 to N instead of rendering a single block, (2) adding `focus`/`bridge` rendering with new visual styling, (3) updating the JSON validation in `lessons.cjs`, (4) updating prompt templates, and (5) regenerating lessons.

**Primary recommendation:** Refactor `renderPart` in-place (same signature, new accumulation behavior), add `focus`/`bridge` field validation to `lessons.cjs:loadModule`, update both prompt templates to require the new fields, then regenerate all 6 lesson JSONs.

### Pattern 1: Pure Renderer Function
**What:** `renderPart()` is a pure function that takes lesson data + indices, returns an ANSI string. No stdout writes.
**When to use:** Always -- the navigator calls renderFn and writes to stdout.
**Current signature (KEEP):**
```javascript
function renderPart(lesson, partIndex, totalParts, currentLessonIndex, totalLessons)
```
**Accumulation change:** Instead of rendering `lesson.content[partIndex]`, loop from `0` to `partIndex` rendering all blocks.

### Pattern 2: Content Section Rendering
**What:** `renderContentSection(section, parts)` handles text/code/project types by pushing to a parts array.
**Reuse:** This function is already shared between `renderLesson` and `renderPart`. Continue using it for each accumulated block.

### Pattern 3: Field Validation at Load Time
**What:** `lessons.cjs:loadModule()` validates required fields per lesson: `['id', 'title', 'lessonNumber', 'objective', 'content', 'conceptMap', 'successCriteria']`.
**Extension needed:** Add per-content-item validation that `focus` and `bridge` exist on every content item.

### Pattern 4: Template-Based Prompt Generation
**What:** `prompt-templates.cjs:assemblePrompt()` does `{{KEY}}` replacement. Templates are `.prompt.md` files.
**Extension needed:** Update the JSON schema examples in both prompt templates to include `focus` and `bridge` fields.

### Anti-Patterns to Avoid
- **Changing navigator.cjs:** The navigator already passes `partIndex` to `renderFn`. Accumulation is purely a renderer concern. Do NOT touch navigator logic.
- **Making renderPart impure:** Keep it returning a string. Do not add stdout writes.
- **Optional focus/bridge fields:** The user explicitly said REQUIRED. Fail at load time, not render time.
- **Dimming prior blocks:** User explicitly said "prior blocks render at normal brightness (not dimmed)."

## Common Pitfalls

### Pitfall 1: Concept Map Part Indexing
**What goes wrong:** The concept map is a synthetic "extra part" appended after content blocks. When accumulating, the concept map part needs special handling -- it should appear as the final accumulated block, not mixed with content.
**Why it happens:** `totalParts = lesson.content.length + (lesson.conceptMap ? 1 : 0)`. The concept map lives at `partIndex === lesson.content.length`.
**How to avoid:** When accumulating blocks 0..partIndex, check if each index is a concept map index. Only accumulate concept map when partIndex reaches it. Give concept map a default focus like "Architecture Overview" (no bridge needed since it is always followed by success criteria on the last part).

### Pitfall 2: Bridge on Last Content Item Must Reference Next Lesson
**What goes wrong:** The bridge field in JSON is a static string. It cannot dynamically know the next lesson title at render time.
**Why it happens:** Lessons are self-contained JSON files. Cross-lesson references must be baked into the JSON during generation.
**How to avoid:** When generating/regenerating lessons, the prompt must include information about the NEXT lesson's title so the LLM can write a bridge that references it. The last lesson's last block bridges to module completion. `generate-lessons.cjs` already has the full LESSON_PLAN array -- pass next-lesson title context.

### Pitfall 3: Test Fixture Updates
**What goes wrong:** Existing tests create lesson fixtures WITHOUT `focus` and `bridge` fields. After adding required field validation, those tests will break.
**Why it happens:** Tests in `lessons.test.cjs` and `renderer.test.cjs` use minimal fixture objects.
**How to avoid:** Update ALL test fixtures to include `focus` and `bridge` on every content item. This is mechanical but must not be forgotten.

### Pitfall 4: Screen Height with Accumulated Content
**What goes wrong:** By the last part (all blocks accumulated), the content may be very long, pushing the navigation footer off-screen.
**Why it happens:** Progressive accumulation means the last part renders ALL blocks.
**How to avoid:** This is by design ("user scrolls up to review"). Ensure the navigation footer and progress dots are always at the bottom of the output. No special handling needed -- the user explicitly chose "no collapsing."

### Pitfall 5: Bridge Section Border Style
**What goes wrong:** A bridge section needs visual distinctness from regular content but should not be too heavy.
**How to avoid:** Use Unicode box-drawing characters (e.g., `\u2502` vertical line, `\u250C`/`\u2510`/`\u2514`/`\u2518` corners) styled dim. Keep it lightweight -- 1-2 lines max. This is Claude's discretion area.

## Code Examples

### Accumulation Loop in renderPart (proposed)
```javascript
// Instead of rendering only lesson.content[partIndex]:
for (let i = 0; i <= partIndex; i++) {
  const isConceptMapPart = lesson.conceptMap && i === lesson.content.length;
  const isCurrent = (i === partIndex);

  if (isConceptMapPart) {
    // Render concept map with focus
    parts.push(style('Architecture Overview', 'dim'));
    parts.push('\n\n');
    parts.push(renderConceptMap(lesson.conceptMap));
  } else {
    const section = lesson.content[i];
    // Focus line
    const marker = isCurrent ? style('\u25B6 ', 'cyan') : '  ';
    parts.push(marker + style(section.focus, 'dim'));
    parts.push('\n\n');
    // Content
    renderContentSection(section, parts);
    // Bridge (except on last accumulated block if it's also the last part overall)
    if (section.bridge && i < partIndex) {
      parts.push(renderBridgeSection(section.bridge));
    } else if (section.bridge && isCurrent && partIndex < totalParts - 1) {
      // Show bridge teaser for current block (it points forward)
      parts.push(renderBridgeSection(section.bridge));
    }
  }

  // Dim separator between blocks (not after the last one)
  if (i < partIndex) {
    parts.push(horizontalRule(60));
    parts.push('\n\n');
  }
}
```

### Bridge Section Rendering (proposed)
```javascript
function renderBridgeSection(bridgeText) {
  const parts = [];
  parts.push(style('\u250C' + '\u2500'.repeat(58) + '\u2510', 'dim'));
  parts.push('\n');
  parts.push(style('\u2502 ', 'dim') + style(bridgeText, 'dim'));
  parts.push('\n');
  parts.push(style('\u2514' + '\u2500'.repeat(58) + '\u2518', 'dim'));
  parts.push('\n\n');
  return parts.join('');
}
```

  const item = lesson.content[i];

## Open Questions

1. **Bridge display on current (last accumulated) block**
   - What we know: Bridge text connects current block to the next one. It makes sense to show it on the current block as a teaser.
   - What's unclear: Should bridge be shown on the last block of the last part? The user said "last lesson's last block bridges to module completion" -- so yes, always show bridge.
   - Recommendation: Always show bridge on current block. The content of the bridge handles what it points to.

2. **Concept map focus/bridge**
   - What we know: Concept map is a synthetic part, not a content item. It has no JSON fields.
   - What's unclear: User listed this as Claude's discretion -- should concept map get hardcoded focus/bridge?
   - Recommendation: Give concept map a hardcoded focus string ("Architecture Overview" -- same as current header). No bridge since it is typically the second-to-last part, followed by success criteria.

3. **generate-lessons.cjs regeneration process**
   - What we know: The script generates prompts, then the user feeds them to an LLM manually, then runs `--from-json` to validate and copy.
   - What's unclear: Whether "re-run generate-lessons.cjs for all 6 lessons" means just regenerate prompts (then manually run through LLM) or if there is now an automated pipeline.
   - Recommendation: Update prompt templates and LESSON_PLAN, regenerate prompt files, then manually feed to LLM and validate with `--from-json`. The existing workflow is manual.
