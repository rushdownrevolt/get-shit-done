2. **Code block**: Show actual .planning/ directory tree (parsed from real GSD project structure):
```
.planning/
  PROJECT.md          # What this project is and why
  REQUIREMENTS.md     # What we need to build
  ROADMAP.md          # Phases, milestones, ordering
  STATE.md            # Where we are right now
  config.json         # GSD configuration
  phases/             # Per-phase execution records
    01-feature-name/
      01-01-PLAN.md
      01-01-SUMMARY.md
  codebase/           # Auto-generated code maps
  learn/              # Learning progress (you!)
```
   - highlight lines for the 4 core artifacts (PROJECT, REQUIREMENTS, ROADMAP, STATE)

3. **Text block**: Explain the planning lifecycle as a pipeline. Each artifact feeds into the next. PROJECT.md defines the what and why. REQUIREMENTS.md breaks it into measurable items. ROADMAP.md sequences them into phases. STATE.md tracks live position. This is NOT waterfall -- artifacts are living documents that update as understanding grows.
   - focus: "Pipeline of living artifacts"
   - bridge: "The lifecycle has a specific order. Let's trace it."

4. **Code block**: Show the lifecycle flow (parsed/inspired by the actual GSD workflow sequence):
```
/gsd:kickoff          Creates PROJECT.md
      |
      v
/gsd:requirements     Creates REQUIREMENTS.md
      |                 (maps to PROJECT.md scope)
      v
/gsd:roadmap          Creates ROADMAP.md
      |                 (phases from requirements)
      v
/gsd:plan-phase       Creates PLAN.md files
      |                 (tasks from phase goals)
      v
/gsd:execute-phase    Creates SUMMARY.md files
      |                 (records what happened)
      v
/gsd:complete-milestone  Archives & tags
```
   - highlight the command names

5. **Text block**: Explain the key insight -- each command reads from previous artifacts and writes new ones. /gsd:roadmap reads REQUIREMENTS.md to know what to sequence. /gsd:plan-phase reads ROADMAP.md to know what the phase goal is. This chain of reads creates traceability: you can always trace a task back to the requirement that spawned it.
   - focus: "Read-previous, write-new creates traceability"
   - bridge: "Within each phase, there's another cycle."

6. **Text block**: Explain the phase execution cycle: discuss (optional context gathering) -> research (optional technical research) -> plan (create PLAN.md with tasks) -> execute (run tasks, produce SUMMARY.md) -> verify (check must-haves against reality). Each phase directory accumulates these records.
   - focus: "Five-step phase execution cycle"
   - bridge: "In the next lesson, we'll zoom into PROJECT.md -- the artifact that starts everything."

7. **Code block**: Show a real phase directory structure:

  12-02-SUMMARY.md    # Its record
