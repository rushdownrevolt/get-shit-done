The "skeptic" concept in GSD is implemented through TWO mechanisms: (1) verify-phase.md's goal-backward analysis that proactively questions whether goals were achieved (not just tasks completed), and (2) the plan-checker (gsd-plan-checker) in plan-phase.md that reviews plans for quality BEFORE execution. **Block 1 (text):** Bridge from Lesson 2 -- verify-work tests AFTER building and relies on human observation. But what about gaps humans miss? What about structural problems invisible in the UI? GSD has a built-in skeptic: mechanisms that proactively question whether work actually achieves its goals. This skepticism operates at two levels -- verify-phase challenges outcomes (did the goal get achieved?), and plan-checker challenges plans before execution (is this plan complete enough to succeed?). Focus: "Proactive questioning catches what reactive testing misses." Bridge to seeing goal-backward analysis.

**Block 2 (code, language: text):** Show the verify-phase.md core_principle and the goal-backward process. Read C:/Users/18182/.claude/get-shit-done/workflows/verify-phase.md and extract the establish_must_haves step showing the three-level verification: truths (what must be TRUE), artifacts (what must EXIST), key_links (what must be WIRED). Highlight the three numbered checks.

**Block 3 (text):** Explain goal-backward verification: instead of asking "did all tasks pass?", the verifier asks "what must be TRUE for the goal to be achieved?" This flips the perspective from producer to skeptic. A task "create chat component" can be marked done while the component is a placeholder. Goal-backward catches this because the truth "user can send messages" requires actual wiring, not just file existence. The verifier checks artifacts exist, exports are correct, and critical connections work. Focus: "Flip perspective: start from the goal, work backward to evidence."

**Block 4 (code, language: text):** Show the must_haves structure from plan-phase.md. Read C:/Users/18182/.claude/get-shit-done/workflows/plan-phase.md and extract the must_haves YAML format from the goal_backward section showing truths, artifacts (with path, provides, contains/exports), and key_links (with from, to, via, pattern). **Block 5 (text):** Explain key_links: these are the critical connections where breakage causes cascading failures. "Chat.tsx fetches from /api/chat via useEffect" -- if that fetch call is missing, the component renders but shows nothing. Key_links have regex patterns that the verifier greps for in actual source code. This is not trust-based verification -- it is evidence-based. The verifier reads the actual file and confirms the pattern exists. Focus: "Key links catch the gaps between components -- where stubs hide."

If the checker finds issues, it sends them back for revision -- the planner fixes the plan before any code is written. This prevents the "build first, find out it was wrong later" pattern. Focus: "Catch plan defects before spending execution context on them."
